## Test Strategy

Pyramid: Vitest unit and characterization tests under `play/tests/` (jsdom), then Playwright end-to-end in `tests/`. No eight-user test exists. The frame recorder `e2eHooks.startFrameRecording()` exists (`2e2631fc0`, `play/src/front/Utils/E2EHooks.ts`) and is unit-tested (`play/tests/front/Utils/E2EHooksFrameRecorder.test.ts`), but no Playwright spec calls it: `rg stopFrameRecording tests/` finds only the type stub at `tests/tests/utils/gameCoordinates.ts:21` (MEASURED, grep). Since `560239d63` the frame probe is in git as `benchmark/frame-probe` (Playwright-driven, outside `tests/`), and `frame-probe gate1` reads GPU time with 999 synthetic walkers; it is a command run by hand, and no CI job or test asserts a time (row N-04). Green means the `play` CI job passes: `npm run typecheck`, `npm run lint`, `npm run pretty-check`, `npm test`. For `GameScene.ts`, `GameSceneMovement.test.ts` must also pass unchanged.

- Legacy code here means code without tests. Before any change to `GameScene.ts`, its change points get characterization tests. These tests pin what the code does today, including its quirks. They do not pin what the code should do.
- Coverage grows along the paths the program changes: the movement path and the remote-player path. These are where the eight-user freeze (H02, H15) and the 1,000-user cost are decided.
- Tests run at pinch points, not at every method:
  - **P1: `update(time, delta)`, remote-player section (`GameScene.ts:1412-1518`).** Every remote join, move, detail change and leave is buffered in `RemotePlayersRepository`. It reaches the scene only here, through `doAddPlayer`, `doUpdatePlayerPosition`, `doUpdatePlayerDetails` and `doRemovePlayer`. Every drawn remote position comes from `PlayersPositionInterpolator.getUpdatedPositions(time)` in this same block. Tests at P1 cover the repository, the interpolator, `PlayerMovement` and the scene's player map together.
  - **P2: `handleCurrentPlayerHasMovedEvent` → `pushPlayerPosition` (`:4290-4408`).** Every local move reaches the server (`connection.sharePosition`), map scripts (`iframeListener.hasPlayerMoved`), the map position and the activatable-distance update only through this path.
  - **P3 (not covered yet): the conversation-bubble block in `update()` (`:1499-1534`).** It covers H01 and GS-05.
- Harness: the real constructor, with a fake `Room`. Methods that need a running Phaser game are replaced on the instance (Subclass and Override, applied to the instance). Collaborators are injected as fields for sensing. DOM-bound singletons are spied. No product file was edited to get the scene under test.
- Bugs found while characterizing are pinned with their ledger ID. Each is fixed in a separate behavior patch whose test flips.

### Local gate (`scripts/gate.sh`, `e5fe9542c`, `78c0055b2`)

One command for the checks a change to `play` or `back` needs. It is a developer tool: no CI workflow calls it, and CI wiring waits for the owner (see Phase 8 in `docs/ARCHITECTURE-OPTIMIZATION-PLAN.md`).

```bash
scripts/gate.sh play [base-ref]
scripts/gate.sh back [base-ref]
```

What it runs, from the script (read at `75db31b6d`):

| Package | Steps | Notes |
|---|---|---|
| play | `i18n` (`typesafe-i18n` then `i18n:check`, first, because its output feeds the type checks), then side by side: `typecheck`, `svelte-check`, `eslint` and `prettier --check` on the changed files, `vitest run` | The whole package for type checks and tests. Lint and format only on the `.ts` and `.svelte` files changed since `base-ref` (default `HEAD`), untracked files included. |
| back | side by side: `tsc --noEmit`, `npm run lint`, `eslint` and `prettier --check` on the changed files, `vitest run` | Same rule for the changed files. |

- **Lock.** A machine-wide lock (`${TMPDIR:-/tmp}/workadventure-gate.lock`, made with `mkdir`) makes a second gate wait for the first, so two sessions do not starve each other. The wait is `GATE_LOCK_WAIT_S` (default 1800 s), then exit 75. A lock whose holder is dead is removed.
- **Output.** Each step prints its exit code and duration. The logs go to `<git-dir>/gate-logs/<package>/<step>.log`. The last line is `gate <package>: PASS|FAIL in <s>s`, and the exit code is 0 or 1.
- **Rerun of failed files.** Steps run side by side take CPU from tests that measure real time. When `vitest` fails, the gate reruns the failed test files once, alone (step `vitest-alone`). A file that passes alone is listed on a `FLAKY under load` line, the vitest step is marked "not counted: the failed files passed alone", and the gate passes. A file that fails alone fails the gate. The first failure stays in the output and in `vitest-first.log`. `GATE_SERIAL=1` runs the steps one after the other and skips the rerun. The gate reports a flaky file; it does not hide it, and the file is fixed at its cause (decision 2026-11-19 in the plan; `c17badfc5` is the example).
- **Checked.** Two probes: a test that fails only on its first run (gate passes, file listed) and a test that always fails (gate fails) (`78c0055b2` message).

Two caveats the gate does not remove:

1. **The module cache and `import.meta.glob`.** The on-disk module cache keys a module by its own source, so a module that expands a glob went on serving the old file list after a file was added, renamed or deleted (`7f75ff086`: `AnalyticsEventCatalog.test.ts` failed with ENOENT on a renamed file until the cache was removed). A plugin in `play/vite.config.ts` now refuses to cache such a module. A new module that expands a glob is covered; a cache problem of another kind is not.
2. **A timing test must not wait on the wall clock.** `RoomTimelineCharacterization.test.ts` waited 50 ms against a 100 ms timer and failed in 1 of 6 gate runs, and passed alone 3 times of 3 (`78c0055b2` message). The cause was the wait, not the gate, so `c17badfc5` moved the file to fake timers. The rerun is a safety net that reports; the fix for a flaky file is a test that drives its own clock.
