# Testing

Safety net of the remove-technical-debt journey (tracker: `docs/REMOVE-TECHNICAL-DEBT-PLAN.md`). Phase 1 for `play/src/front/Phaser/Game/GameScene.ts` ran on 2026-11-12; its evidence is `docs/audits/tech-debt/phase1-gamescene/README.md`.

## Test Strategy

Pyramid: Vitest unit and characterization tests under `play/tests/` (jsdom), then Playwright end-to-end in `tests/`. No eight-user or browser-performance test exists. Green means the `play` CI job passes: `npm run typecheck`, `npm run lint`, `npm run pretty-check`, `npm test`. For `GameScene.ts`, `GameSceneMovement.test.ts` must also pass unchanged.

- Legacy code here means code without tests. Before any change to `GameScene.ts`, its change points get characterization tests. These tests pin what the code does today, including its quirks. They do not pin what the code should do.
- Coverage grows along the paths the program changes: the movement path and the remote-player path. These are where the eight-user freeze (H02, H15) and the 1,000-user cost are decided.
- Tests run at pinch points, not at every method:
  - **P1: `update(time, delta)`, remote-player section (`GameScene.ts:1412-1518`).** Every remote join, move, detail change and leave is buffered in `RemotePlayersRepository`. It reaches the scene only here, through `doAddPlayer`, `doUpdatePlayerPosition`, `doUpdatePlayerDetails` and `doRemovePlayer`. Every drawn remote position comes from `PlayersPositionInterpolator.getUpdatedPositions(time)` in this same block. Tests at P1 cover the repository, the interpolator, `PlayerMovement` and the scene's player map together.
  - **P2: `handleCurrentPlayerHasMovedEvent` → `pushPlayerPosition` (`:4290-4408`).** Every local move reaches the server (`connection.sharePosition`), map scripts (`iframeListener.hasPlayerMoved`), the map position and the activatable-distance update only through this path.
  - **P3 (not covered yet): the conversation-bubble block in `update()` (`:1499-1534`).** It covers H01 and GS-05.
- Harness: the real constructor, with a fake `Room`. Methods that need a running Phaser game are replaced on the instance (Subclass and Override, applied to the instance). Collaborators are injected as fields for sensing. DOM-bound singletons are spied. No product file was edited to get the scene under test.
- Bugs found while characterizing are pinned with their ledger ID. Each is fixed in a separate behavior patch whose test flips.
- SocketManager (Phase 1, 2026-11-12, `play/tests/pusher/SocketManagerRoomTraffic.test.ts`, evidence in `docs/audits/tech-debt/phase1-socketmanager/`). Pinch points:
  - **P1: the per-socket back stream handlers of `handleConnectToRoom` (`SocketManager.ts:281-286` registers them; `handleMessageFromBack` `:322-366`, `closeSocketWhenBackEnds` `:368-401`, `closeSocketWhenBackFails` `:403-431`).** Every message from the back to one browser passes through `handleMessageFromBack`. The `end` and `error` handlers decide when the pusher closes the socket.
  - **P2: `handleUserMovesMessage` and `handleViewport` (`:650-689`).** Every move reaches the back here, and every viewport reaches the room's zone subscriptions here.
  - **P3: the per-room stream into the `ZoneEventListener` callbacks (`:691-728`, `:1046-1097`).** One zone event fed into the room stream covers `PusherRoom`, `PositionDispatcher`, `Zone` and the callbacks, and the test reads what each socket receives.
  - **P4: `cleanupSocket` (`:615-648`).** Zones, room, back stream and spaces are all released from here.
  - **P5: `handleJoinSpace` (`:510-599`).** The only place that creates a `Space` and adds a socket to it.
  - Harness: a real `SocketManager` with real rooms, zones and spaces. The back is a fake `apiClientRepository.getClient` (import seam) that returns fake gRPC streams. The space back is a fake `SpaceConnectionInterface` passed to the existing constructor parameter. No product file was edited to get the manager under test.
- MediaStore (Phase 1, 2026-11-12, `play/tests/front/Stores/MediaStoreGetUserMedia.test.ts`, evidence in `docs/audits/tech-debt/phase1-mediastore/`). Pinch points:
  - **P1: `mediaStreamConstraintsStore` (`MediaStore.ts:532-641`).** All 15 inputs (user requests, room media flags, away mode, energy saving, status, the batch flag, audio streaming) meet here, and it decides what the browser is asked for. A test reads its effect as the `getUserMedia` calls that follow.
  - **P2: `runRawStreamUpdate` behind `rawLocalStreamStore` (`MediaStore.ts:869-1058`).** The only caller of `getUserMedia`. `planTracks` (`:846-867`) decides which tracks to stop and which to request; `runRawStreamUpdate` stops them, reuses the warm microphone track, and requests the rest.
  - **P3: `handleGetUserMediaFailure` (`:781-827`), called from `runRawStreamUpdate`'s `catch` (`:1046-1054`), and the `navigator.mediaDevices` branches at the top of `runRawStreamUpdate` (`:874-898`).** They decide which device a failure turns off and which access issue is recorded.
  - **P4: the away and energy-saving inputs of P1** (`privacyShutdownStore` through `mediaHeldByStatus`; `cameraEnergySavingStore` and its three timers, `:166-247`, `:379-417`).
  - **P5: the update queue and its generation check (`:912-917`, `:1033-1054`).** A change during a pending request makes that request stale.
  - **P6: `deviceListStore` and its module-scope subscription (`:1534-1571`, `:1669-1731`).** The only caller of `enumerateDevices`. A removed device in use triggers a new request.
  - Harness: the real `MediaStore` module graph, loaded fresh in each test (`vi.resetModules()` and a dynamic import). Fakes only at the browser boundary: `navigator.mediaDevices` (a queue of answers for `getUserMedia`, `enumerateDevices`, `devicechange`), `MediaStreamTrack` objects, timers, `document.hasFocus` and window `focus`/`blur` events, and `localStorage` preferences. One link seam: `GameManager` is mocked to break the import cycle MD-07. One structural fake: the game scene's space registry, set through `gameSceneStore`, for the "our audio is streamed" flag. No product file was edited to get the module under test.
- RoomTimeline (Phase 1, 2026-11-12, `play/src/front/Chat/Components/Room/RoomTimelineCharacterization.test.ts`, evidence in `docs/audits/tech-debt/phase1-roomtimeline/`). Pinch points:
  - **P1: `buildRenderItems` (`RoomTimelineRenderItems.ts:54-112`), called from `renderItems` (`RoomTimeline.svelte:242-246`).** Every timeline change meets here. `buildRenderItems` inserts the day separators and their labels, and decides which message shows its sender header and which shows its time; `renderItems` hands the previous render's rows back for reuse. A test reads its effect as the rows, the separator labels, and the props each message row receives.
  - **P2: the open sequence (`onMount`, `initMessages`, `fillViewport`, `loadUntilReadMarker`, `retryLoading`, `:355-449`).** It initializes the timeline, fetches older pages, and chooses the loading, error, empty or message state.
  - **P3: the last-item effect (`:511-559`).** A new last message scrolls a pinned list to the bottom, is counted on the jump button while the user reads history, or scrolls back for the user's own message.
  - **P4: the read effect (`:488-509`).** It calls `room.setTimelineAsRead()` when the room opens, on every new last message, and when a hidden tab becomes visible. In a Matrix room each call sends a read receipt that every other member receives.
  - **P5: back-pagination (`handleScroll`, `loadMorePreviousMessages`, `shouldLoadMoreMessages`, `:675-729`).** A scroll near the top fetches one older page after 100 ms, one page at a time.
  - **P6: focus requests (`$roomTimelineFocusStore` effect, `focusPendingTimelineRequestOrScrollToBottom`, `focusTimelineEvent`, `:233-237`, `:457-470`, `:741-777`).** A search result, a poll or a thread asks the timeline to show one event.
  - Harness: the real component mounted with Svelte's `mount`, as in `RoomTimelineRowReuse.test.ts`. Fakes only at the boundaries: a structural fake room (its stores and the methods the timeline calls), a stand-in `Message.svelte` that records the props of each row, the `GameManager` and `UIWebsiteManager` modules, the four children outside the list, `ResizeObserver`, and the layout that jsdom lacks (`scrollHeight`, `clientHeight`, `scrollTop`, `scroll`, `scrollIntoView`, `document.visibilityState`). The `en-US` locale is loaded, so the tests read the user's text. No product file was edited to get the component under test.
  - Harness additions (Phase 2): stand-ins for `PollCard.svelte`, `QuestionCard.svelte` and `MessageSystem.svelte`, so a test can put those rows in the list without their stores. The day-label tests fix the clock with `vi.setSystemTime` (Date only; the timers stay real) and `afterEach` restores it with `vi.useRealTimers()`.

## CI Gates

- Existing (`.github/workflows/continuous_integration.yml`, `play` job): `npm run typecheck`, `npm run lint`, `npm run pretty-check`, `npm test`. `GameSceneMovement.test.ts` runs inside `npm test` with no new step.
- Heap condition (GS-08): importing `GameScene` needs more than the default heap of a 3 GB container.
