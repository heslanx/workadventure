# fix(map-storage): keep map autosave recoverable and serialized per map

## Trigger

`MapsManager` saves an edited map from a 15 s `setInterval`. The interval is cleared on the first failed
write, a tick does not check whether the previous write finished, and the map is evicted from memory 30 s
after its last command whether or not it was saved. Commands that change the WAM outside
`mapsManager.executeCommand` (custom entity commands, which `MapStorageServer` runs through
`entitiesManager`) never schedule a save at all.

## Reproduced on trunk

`map-storage/src/tests/MapsManagerAutosave.test.ts` drives the public `MapsManager` calls against an
in-memory `FileSystemInterface` whose writes can fail or be held open, with fake timers. Run against trunk
(`ddbe245a8`): 10 failed, 5 passed (15 tests).

| Scenario | Trunk result |
|---|---|
| First write fails, storage recovers, no further edit | The edit is never stored (`expected undefined to be 'cmd-1'`). |
| Write slower than the interval | Three writes of the same map in flight (`expected 3 to be 1`). |
| Same, older write finishes last | Storage ends with the older state (`expected 'cmd-1' to be 'cmd-2'`). |
| Command history expires while every write fails | The map is evicted unsaved, a reload returns the pre-edit file. |
| Edit lands during a write that then succeeds | Not reproduced: trunk stores the newer edit at the next tick. |
| WAM changed by a command that is only queued (custom entity commands) | Never stored. |
| Every write fails for 10 minutes | The map is not retried at all, so the logging test fails on its attempt count (`expected 1 to be 40`). |
| Edits continue near the end of the retry horizon | Never stored (trunk does not retry). |
| A write never settles | Not reproduced: trunk starts a new write every interval regardless. |

Five of the 16 tests pass on trunk: four regression guards (persist-and-release, stop retrying after
replace/delete, follow-up write for an edit during a write, no retry of the abandoned state after an upload)
and the write-that-never-settles test, which trunk passes because it starts a new write every interval (row
above). The upload guard settles the held write with a failure, so it covers retries only (see "Not
guaranteed"). Measured on the 15-test revision (10 failed, 5 passed); the 16th test, a logger that throws
inside a completion handler, was not run against trunk.

The stale overwrite needs the older write to finish after the newer one. The fake storage orders
completions on demand. No real backend was used, so no frequency is claimed.

## Resulting behavior

One explicit save state per map key replaces the interval and timestamp maps:
clean, dirty, saving, saving+dirty, retrying.

- At most one write in flight per loaded map instance. A write starts only from dirty or retrying. Two
  exceptions: after `clearAfterUpload` drops a map whose write is in flight, a reload plus an edit starts a
  new write 15 s later while the old one may still be running; and a write that has not settled after
  5 minutes (`SAVE_WRITE_TIMEOUT_MS`) is counted as failed and retried while it may still be running.
- An edit made during a write keeps the map dirty and gets a follow-up write, with no further edit needed.
- A failed write is retried every 15 s with the current WAM, one attempt at a time.
- Every queued command marks the map unsaved (`addCommandToQueue`), because it changes the WAM's
  `lastCommandId` and, for custom entity commands, the WAM itself. On the `executeCommand` path this is a
  no-op on top of the existing mark. Custom entity upload and modify, file upload and error commands only go
  through `addCommandToQueue` (`MapStorageServer.ts`), so each burst of them now causes one coalesced WAM
  write where trunk wrote none.
- A write that never settles is failed by a 5 minute timer, so the map is retried instead of staying in
  "saving" forever.
- A map with unsaved changes is not evicted when its command history expires. Eviction still runs under the
  edition lock, when the queue is empty and the map is clean.
- One visible difference on the healthy path: a map whose command failed before it was queued is now
  evicted after its save. On trunk it was saved the same way but stayed loaded, because only queue expiry
  evicted.
- When an attempt fails 1 hour or more after the newest unsaved edit (`SAVE_RETRY_HORIZON_MS`), the save is
  abandoned and reported, and the map becomes evictable. The horizon counts from the newest edit, not the
  oldest, so a map that is still being edited during an outage keeps being retried. During an outage this
  bounds memory to the maps edited in the last hour, one `WamFile` each, plus, on a backend whose writes hang,
  the serialized payload of every timed-out write still in flight: up to about 12 per map per hour (one per
  5 minute timeout). The S3 client's 60 s request timeout limits this; `DiskFileSystem` and long queueing in
  `s3UploadConcurrencyLimit` do not.
- Failures: `console.error` with map key, attempt and time since the newest edit on the first attempt of a
  streak and then every 20th attempt (every 5 minutes), not every 15 s. Abandonment is always logged.
  Sentry on the first failure of a streak and on abandonment. A save that succeeds after failures logs one
  `console.info` with the number of failed attempts.
- The completion handlers change the save state (retry scheduled, follow-up scheduled, or state removed)
  before they log or report, so a throwing `console` or Sentry call cannot leave a map "saving" without a
  timer. The completion chain ends with a `.catch` that logs and reports to Sentry, so such a throw does not
  become an unhandled rejection.
- `clearAfterUpload` cancels a pending save, retry or write timer. A completion of an older or timed-out
  write is ignored.

## Guaranteed and not guaranteed

Guaranteed, within the scenarios above: an accepted edit is eventually stored once storage recovers within
the horizon and the process keeps running, and writes of one loaded map instance do not overlap unless one
of them exceeded the 5 minute write timeout.

Not guaranteed:

- Durability of the acknowledgement. Edits are still acknowledged once applied in memory. A process stop
  loses whatever is not written yet, as before.
- Cancelling a write already handed to storage. A delete, an upload or a move of a map waits for the
  earlier deletes, uploads and moves of that map, then for its writes, at most 60 s in total, and the map
  stays loaded and editable while it waits. A move saves the unsaved edits of the moved map first, so the
  moved file has them. A delete or an upload drops the edits that no write carried, because it replaces
  that map. If the 60 s run out, or the save before a move fails, the request answers 503 with
  `Retry-After: 60`, storage is unchanged, and the map keeps its edits for the next autosave. Writes and
  replacements from another map-storage instance are not waited for, and neither are the writes in flight
  when the back servers relay `handleClearAfterUpload` for an upload another instance served. A write or
  a replacement that never settles makes every later delete, upload or move of its map answer 503 until it
  settles or the process restarts. Moving a directory of maps, and copying onto a `.wam`, do not wait. A
  timed-out write that lands after its retry leaves the older state in storage for one autosave interval,
  until the map is saved again.
- Anything past the retry horizon.

The WAM format and `FileSystemInterface` are unchanged. The DELETE, PUT, PATCH, zip upload and move
endpoints of `UploadController` now replace stored `.wam` files through `MapsManager.replaceStoredMaps`.
Both upload endpoints delete Multer's temporary file whatever the response.

## Write counts on healthy storage

Measured with the same test schedules on trunk and on this branch (`storage.writesStarted`):

| Schedule | Trunk | This branch |
|---|---|---|
| One edit, then idle | 2 writes | 1 write |
| 13 edits, one every 5 s for 60 s, then idle | 6 writes | 5 writes |

No schedule measured writes more than trunk. Marking unsaved in `addCommandToQueue` does not change the
counts of these two schedules: both assertions pass with it. It adds a write source these schedules do not
exercise: queue-only commands (custom entity upload and modify, file upload, error), which trunk never
wrote. Each write carries the same payload (the whole WAM), so bytes
follow the counts. Write latency was not measured.

## Limitations

- Deterministic fault injection only. No run against a real disk or S3-compatible backend.
- No live editor session, no restart test, no multi-instance test.
- The 1 hour horizon, the constant 15 s retry, the 5 minute write timeout and logging every 20th attempt
  are proposals, not measured values. Each attempt still serializes the whole WAM; there is no backoff.
- No flush on shutdown.

## Rollback

Revert the commits. They touch `map-storage/src/MapsManager.ts` and `map-storage/src/Upload/UploadController.ts`
and add two test files. No data format, configuration, dependency or API changes, so trunk behavior returns
as it was. While a write is in flight, the upload endpoints answer 503 where trunk answered 200 and could
restore the old map.
