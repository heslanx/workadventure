# perf(pusher): skip zone reconciliation when a viewport keeps covering the same zones

## Why

Every viewport update rebuilt the full set of zone keys of the viewport, diffed it against the socket's listened
zones and split the keys back to numbers, even when the viewport moved a few pixels and covered exactly the same
zones. At 320 px zones and 1080p viewports, most movement updates stay in the same zones.

## What changes

- `PositionDispatcher` remembers, per socket, the zone rectangle its last viewport was fully reconciled to
  (`lastZoneRectangles`, a `WeakMap<PusherWebSocket, ZoneRectangle>`).
- After the existing validation and the centered 1600-zone crop, `setViewport` returns early when the new effective
  rectangle equals the reconciled one.
- The remembered rectangle is cleared before reconciling and set after it, so a subscription that throws halfway
  never makes a later update skip work. `removeViewport` deletes the entry.
- The reconciliation body moves unchanged into a private `reconcileZones()`. Keeping it inline made every
  all-miss update 6-12% slower in the benchmark below; extracting it brought that back within noise.

Unchanged: invalid-viewport rejection and warning, the crop and first-oversize warning, first/last-listener zone
subscription to the back, the exact viewport stored by `SocketManager`, the protocol. No new dependency.

## Tests

13 new cases in `play/tests/pusher/PositionDispatcher.test.ts` assert subscriptions and socket events, not the
cache: same viewport again, movement inside the same zones (also in negative coordinates), crossing a boundary
(each zone entered and left once), coming back to a zone, enter/leave notifications, floor and inclusive edges,
moving a cropped window, an invalid viewport after a valid one, shared zones (first and last listener) and remove
then re-add. They pass on the current code and on this change (21/21). A mutant without the invalidation in
`removeViewport` fails `subscribes again when a socket sends the same viewport after its viewport was removed`.

## Measurements

Single-process micro-benchmark of `setViewport` (2 CPUs, Node 24), implementations interleaved per replay, two
copies of the current file as an A/A noise reference (base2/base medians 0.93 to 1.10). Median time per update
relative to the current code, final version, run 4 (and run 5):

| Scenario | effective-bound hit ratio | time vs current | bytes/update current -> this PR |
|---|---|---|---|
| same viewport repeated (1080p) | 100% | 0.007 (0.007) | 6665 -> 120 |
| move inside the same zones (1080p) | 100% | 0.007 (0.007) | 6609 -> 120 |
| walk, 26 px per update (1080p) | 84% | 0.268 (0.262) | 7491 -> 2032 |
| 1,000 sockets walking, round-robin | 84.1% | 0.281 (0.282) | 7264 -> 1639 |
| cross a zone every update (1080p) | 0% | 1.011 (1.013) | 16855 -> 17500 |
| cross a zone every update (40x40 zones) | 0% | 1.027 (0.983) | 265094 -> 265153 |
| move inside the same zones (40x40 zones) | 100% | 0.000 (0.000) | 195959 -> 123 |

The zone subscription/unsubscription trace and the resulting zone membership hash are identical to the current
code in every scenario.

## Limits

This is a micro-benchmark of one function. It is not a live measurement with 1,000 users: WebSocket traffic,
encoding, the back connection, event-loop lag and GC of a real pusher are not included, and the hit ratios come
from synthetic trajectories (26 px per update). `npm run typecheck` was not run for this change.
