# A05 proposal - timeline projection and navigation (D06)

Decision: **keep virtualization conditional.** Do not introduce a render window now. A05's ownership deepening (projection plus anchors in one module) stays "worth exploring"; a virtualized list is gated on a real-browser profile.

## What the jsdom measurement says (and does not say)

From `README.md` section 1 (container `wa-fable-h8`, 1 CPU, jsdom 29.1.1, Svelte 5.55.9, no layout engine):

- Projection is not the cost: one append into the proximity timeline store takes a median 0.011 / 0.050 / 0.114 ms at 20 / 500 / 2000 loaded messages; the unread helpers take 0.004 / 0.023 / 0.127 ms.
- The DOM grows linearly with loaded history: about 21.2 element nodes per real `Message.svelte` (424 / 10,584 / 42,332 nodes at 20 / 500 / 2000 messages), and mounting them took 0.39 / 3.7 / 8.3 s of script time in that container.

- In the real `RoomTimeline.svelte`, appending one message takes a median 43 / 252 / 1013 ms of script time at 20 / 500 / 2000 loaded items (run 4), roughly linear in history, while the store projection for the same append stays near 0.1 ms. The growing part is in the view, not the provider. Which part of the view (row derivation, keyed `each` reconciliation, effects walking the list) is not yet attributed.

So the first candidate fix is not a render window: it is to find the view work that scales with loaded items on every append and make it proportional to the change. That fits A05 (projection and anchors owned by one module) and may remove most of the per-append growth without virtualization. A render window remains a separate, later option for DOM size.

That makes "all loaded items stay in the DOM" a measured structural fact, and node count a real input to style/layout cost. It does not measure style recalculation, layout, paint, memory or typing latency in a browser, and it does not show that users of the incident had 500+ messages loaded. Pagination (`loadMorePreviousMessages`) limits what is fetched per page, not what accumulates in the DOM.

## Gate

| Condition | Measured how | Then |
|---|---|---|
| in a browser, one incoming message with the chat open costs visibly more at 2000 loaded items than at 20, beyond the spread of two repetitions | Performance trace of that single append (which function owns the time) | make that view work proportional to the change (A05 ownership of projection and anchors); re-measure before any render window |
| with the incident's typical history (count loaded messages), chat open vs closed changes frame deltas or typing latency beyond the spread of two repetitions | browser Performance trace, runbook `../W0/README.md` section 3 step 3 | render window with overscan and stable keys, keeping scroll anchor, unread line, focus, threads, replies, redaction, keyboard navigation, read receipts; decide browser find/selection behavior explicitly |
| no difference at realistic history sizes | same trace | close H05 without virtualization; keep A05 only as an ownership/readability debt |
| difference only at very long sessions | heap snapshots at equal checkpoints (H10) | look at retention first; a smaller window does not by itself reduce retained history |
